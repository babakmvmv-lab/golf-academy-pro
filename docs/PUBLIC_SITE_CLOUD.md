# فضای ابری مستقل سایت و فروشگاه

## ساختار نهایی: یک پروژه، دو فضای مستقل

در **همان پروژهٔ Supabase فعلی**، مسیرها از هم جدا هستند:

| بخش | مخزن داده | مسیر نوشتن | حساب/صف |
|---|---|---|---|
| آکادمی | `ga_store` و جدول‌های فعلی آکادمی | `ga-sync` فعلی | حساب‌ها و صف فعلی آکادمی، بدون تغییر |
| سایت و فروشگاه | **`web_store` مستقل** | **`web-sync` مستقل** | حساب مدیر وب، صف و cache مستقل |

صرفاً پیشوند جدید داخل `ga_store` استفاده نشده است. کلاینت وب هیچ fallback خواندن/نوشتن به جدول یا تابع آکادمی ندارد. کلیدهایش نیز `web_*` هستند و تابع جدید، کلیدهای `ga_*` را رد می‌کند. کاربران آکادمی، اطلاعات رنک، داده‌ها و تابع آن جابه‌جا نشده‌اند.

`supabase/web_store.sql` فقط جدول و policyهای فضای وب را ایجاد می‌کند. `supabase/functions/web-sync/index.ts` فقط `web_store` را می‌شناسد. هیچ پروژه، هاست، سرور Next یا دیتابیس جداگانه‌ای ایجاد نشده است.

## مشکل قبلی

خروجی استاتیک سایت، مسیرهای سروری `/api/admin/...` را روی GitHub Pages نداشت. مدیریت با پاسخ 404/405 به حالت demo می‌رفت و ذخیره فقط در `puttclub_demo_*` همان مرورگر انجام می‌شد. از طرف دیگر `useSiteSettings` عمومی فقط مقدار ثابت `DEFAULT_SITE_SETTINGS` را برمی‌گرداند؛ بنابراین تنظیمات به نمایش عمومی وصل نبود.

اکنون رابط مدیریت و صفحهٔ عمومی به یک منبع دادهٔ وب متصل‌اند. adapter صریح داده استفاده می‌شود؛ **fetch عمومی مرورگر/Next دستکاری نشده** و API سروریِ جدا برای storefront ساخته نشده است.

## ورود و مجوز انتشار

- مدیر سایت/فروشگاه با **Supabase Auth** وارد می‌شود؛ شناسهٔ انتخاب‌شدهٔ مالک `admin@puttclub.ir` است و نام کاربری `admin` به همان ایمیل نگاشت می‌شود.
- رمز آغازین تصادفی فقط در فایل خصوصی مالک نگهداری می‌شود؛ در کد، git، این سند یا دادهٔ عمومی نیست.
- `web-sync` توکن را با `auth.getUser` اعتبارسنجی می‌کند و فقط `app_metadata.web_admin === true` که سمت سرور تعیین شده را می‌پذیرد. `user_metadata`، نام کاربری محلی یا marker مرورگر مجوز نوشتن نیست.
- `verify_jwt` در gateway تابع جدید خاموش است تا بررسی سازگار در خود تابع انجام شود؛ **هیچ درخواست بدون session معتبر اجازهٔ نوشتن ندارد**.
- نوشتن مستقیم REST برای `anon` و `authenticated` با grant/RLS مسدود است؛ حتی مدیر وب باید از endpoint دارای اعتبارسنجی و CAS عبور کند.
- نشست خصوصی در `puttclub_web_auth_v1` است؛ هرگز وارد صف محتوای عمومی نمی‌شود. refresh، خروج و تغییر رمز وجود دارد. خروج وب session یا حساب آکادمی را دست نمی‌زند.
- نشست محلی قدیمی می‌تواند برای بازیابی پیش‌نویس‌ها باقی بماند، ولی انتشار نیاز به ورود ابری معتبر دارد. فرم ورود قبلی و دو مقصد «پنل سایت/پنل فروشگاه» حفظ شده‌اند.

این حساب مدیر، عضویت فروشگاه یا بازیکن/یوزر آکادمی نیست. حساب‌های خصوصی مشتریان و سفارش‌ها در این انتشار به مخزن عمومی منتقل نشده‌اند.

## چه چیزی ابری است؟

| محتوا | کلید نمونه |
|---|---|
| هویت، لوگو، قالب، تماس، منو، هیرو، درباره و پاورقی | `web_setting_hero`، `web_setting_contact`، ... |
| گیت فروشگاه و checkout | `web_setting_shop_gate` |
| دوره‌ها، متن، تصاویر، چیدمان، ترتیب و فعال‌بودن | `web_course_<id>` |
| نام، قیمت، موجودی، تصاویر و ویژگی‌های کالا | `web_product_<id>` |
| دسته‌بندی‌های فروشگاه | `web_category_<id>` |
| نظرات عمومی تأییدشده | `web_testimonial_<id>` و `web_review_<id>` |

هر بخش و هر رکورد کلید مستقل دارد. تغییر هیرو تماس را بازنویسی نمی‌کند. عکس‌های موجود در ریپو باقی‌اند؛ آدرس تصویر می‌تواند از مدیریت تغییر کند. ظاهر، فونت‌ها، ساختار ویترین و سه ورودی جدا حفظ شده‌اند.

کالای جدید روی همین هاست استاتیک با قالب محصول و query `?item=<slug>` باز می‌شود. اطلاعات، شناسهٔ سبد، breadcrumb و شناسهٔ دیدگاه از کالای واقعی خوانده می‌شوند. App Router/Drizzle یا سرور جدید به پروژه افزوده نشده است.

حذف به شکل tombstone داخلی `_deleted` است تا seed استاتیک دوباره رکورد حذف‌شده را زنده نکند. حذف محصول، دیدگاه‌های عمومی وابسته را نیز علامت می‌زند. تغییر نام دسته، همهٔ رکوردهای وابسته را **قبل از شروع ارسال** در صف ثبت می‌کند.

## حفظ تغییرات و تأیید واقعی

- صف مستقل: `puttclub_cloud_outbox_v1`؛ cache تأییدشده: `puttclub_cloud_cache_v1`.
- تغییر پیش از ارسال در صف ذخیره می‌شود. فقط HTTP موفق به همراه `ok:true`، تعداد دقیق ردیف و stamp تأییدشدهٔ سرور، یا readback دقیق همان مقدار، تأیید است.
- زمان نسخه از سرور می‌آید. `web-sync` از **compare-and-set اتمیک در دیتابیس** استفاده می‌کند: درج نمی‌تواند رکورد موجود را بازنویسی کند؛ به‌روزرسانی فقط با stamp مبنا انجام می‌شود.
- تعارض دستگاه‌ها 409 است، نه overwrite پنهان. پیش‌نویس محفوظ می‌ماند و انتشار نسخهٔ محلی نیازمند تأیید صریح است.
- ACK قدیمی ویرایش جدید را حذف نمی‌کند. صف از آخرین نسخهٔ localStorage به‌روز می‌شود؛ در مرورگرهای دارای Web Locks، انتشار تب‌ها سری است.
- قطع ارتباط، timeout، 401/403، 413 یا پاسخ ناقص، صف را پاک نمی‌کند. دریافت موفق، خطای ارسال را پنهان نمی‌کند. پس از ورود معتبر/اتصال دوباره، retry ممکن است.
- پیام سبزِ ذخیرهٔ قبلی، قبل از تلاش جدید پاک می‌شود. فایل پشتیبان صف فقط با کلیک مدیر ساخته می‌شود.
- کلاینت و تابع مستقل وب، سقف کامل JSON و UTF-8 برابر ۲ MiB دارند؛ داده قطع یا فشرده‌سازی پنهان نمی‌شود.

## ذخیره‌های قبلی مرورگر

مقادیر قدیمی حذف نمی‌شوند و در فرم مدیریت قابل بازیابی‌اند. کادر ابر، دکمهٔ **«انتشار ذخیره‌های قبلی»** را نشان می‌دهد:

- انتقال فقط با تأیید مدیر و ورود ابری مجاز انجام می‌شود؛ بازدیدکننده seed را روی ابر نمی‌نویسد؛
- کلید دارای نسخهٔ ابری خودکار با نسخهٔ محلی کهنه جایگزین نمی‌شود؛
- اگر گیت در نسخهٔ قدیمی خاموش بوده، تأیید جداگانه می‌گیرد؛
- نسخهٔ محلی قدیمی برای بازیابی باقی می‌ماند.

دستگاه جدید در اولین بازدید دادهٔ وب را از ابر می‌خواند. تب همان مرورگر با storage event و صفحهٔ باز فعال هر ۴۵ ثانیه تازه می‌شود؛ نیازی به انتشار مجدد git برای تغییر محتوا نیست.

## گیت و دادهٔ خصوصی

گیت پیش‌فرض روی موبایل و دسکتاپ روشن می‌ماند. رمز گیت به شکل digest ذخیره می‌شود؛ مقدار خالی در فرم یعنی رمز قبلی عوض نشود. تغییر سیاست، نشست قبلی گیت را بازبینی می‌کند. در شکست اتصال اولیه، رمز پیش‌فرض راه فرار نیست.

گیت فروشگاه یک کنترل نمایشی است؛ امنیت انتشار محتوا جداگانه با Auth و مجوز سروری اعمال می‌شود.

رمز و session، حساب مشتری، سفارش، آدرس تحویل، پرداخت و تلفن/ایمیل خصوصیِ نظردهنده **وارد جدول عمومی `web_store` نمی‌شوند**. تابع سرور نیز فیلدهای خارج از فهرست مجاز و نظرات بررسی‌نشده را رد می‌کند. وضعیت‌های بررسی/ردِ محلی و مسیر خصوصی قدیمی در این انتشار بازطراحی نشده‌اند؛ آمار حساب/سفارش در داشبورد صریحاً «محلی» است. توسعهٔ ذخیرهٔ خصوصی فروشگاه باید در بخش وب و با جداول خصوصیِ دارای policy مناسب انجام شود، هرگز در آکادمی یا جدول عمومی محتوا.

## ساخت frontend و cache

```sh
python3 source/build_public_cloud.py
```

سورس در `source/js/site-cloud.js` و adapterهای export فعلی در `source/build_public_cloud.py` است. فایل‌های اصل snapshot برای cache قبلی دست‌نخورده‌اند. bootstrap و ۱۱ chunk سازگار‌شده نام content-hash دارند و ارجاع HTML/RSC با هم تغییر می‌کند؛ فهرست در `source/public-cloud-manifest.json` است. پس از جایگزینی export اولیه، anchorهای سازنده باید بازبینی شوند.

پس از نادیده‌گرفتن URL اسکریپت‌های جدید، markup تمام ۲۲ صفحهٔ HTML با نسخهٔ قبل برابر است. اگر bootstrap بارگذاری نشود، ویترین اولیه می‌ماند ولی ذخیره به حالت demo با موفقیت ساختگی برنمی‌گردد.

## شواهد بررسی

- migration و تابع `web-sync` در همان پروژه ایجاد و آزمایش شدند؛ دسترسی ناشناس 401، کلید آکادمی 400، فیلد خصوصی نامجاز 400 و نوشتن REST مستقیم 403 گرفت.
- یک رکورد تشخیصی یکتای موقت و **فقط tombstone** در `web_store` ایجاد و دقیقاً خوانده شد؛ تکرار با stamp قدیمی 409 گرفت. سپس فقط همان probe حذف و نبودش تأیید شد.
- تعداد ردیف‌ها و fingerprint دادهٔ آکادمی پیش/پس از عملیات یکسان بود؛ هیچ دادهٔ آکادمی جابه‌جا نشد. مقدارهای دادهٔ زنده یا شناسه‌های اعضا وارد این سند و ریپو نشده‌اند.
- پروتکل کلاینت، نقش سروری، جدایی جدول، CAS، صف، خطا/retry، مرورگر مستقل، بازیابی legacy، فرم واقعی گیت و ورود/تغییر رمز/خروج بررسی می‌شوند:

```sh
node source/e2e/site_cloud_e2e.cjs
NODE_PATH=<qa_node_modules> node source/e2e/web_sync_e2e.cjs
NODE_PATH=<qa_node_modules> node source/e2e/site_cloud_browser.cjs
NODE_PATH=<qa_node_modules> node source/e2e/site_cloud_recovery_browser.cjs
NODE_PATH=<qa_node_modules> node source/e2e/web_admin_auth_browser.cjs
```

تست‌های مرورگر از سرویس ساختگی و دادهٔ ساختگی استفاده می‌کنند و ارتباط بیرونی مسدود است. WebKit لینوکس با software compositing آزمایش می‌شود؛ فقط امضای مشخصِ هشدار لغو prefetch استاتیک Next که روی نسخهٔ بدون تغییر `f4762c9` نیز بازتولید شد، جدا شمرده می‌شود.

**مسئلهٔ قدیمی حجم `ga-sync` آکادمی، مسئلهٔ جداگانه است.** این انتشار تابع آن را تغییر نداده و دربارهٔ برطرف‌شدن صف قبلی آکادمی ادعایی ندارد.
